| 类型 | 目标（可测量） |

---

## 2. 重点与难点

- **重点**：测试分层（单元/接口/E2E/压测）各测什么；断言要测"业务真相"。
- **难点**：学生写的断言只测"状态码 200"，不测业务语义。
- **突破**：展示一个"200 但数据错"的案例，让学生设计能抓住它的断言。

---

## 3. 企业情境（Lernsituation）

> 测试负责人："你们上次交付，功能演示全过，上线第二天看板数字和实际对不上。
> 你们的测试到底测了什么？"

## 5. 关键内容

### 5.1 测试金字塔（本项目实际）

| 层 | 数量 | 测什么 | 工具 |
|---|---|---|---|
| 单元 | 106 | 领域规则、口径 | pytest |
| 接口 | 14 | REST/MCP 契约 | TestClient |
| E2E | 13 | 看板与 API 一致、闭环、红线 | Playwright |
| 压测 | 2 套 | 吞吐/延迟 | k6 / Locust |

### 5.2 TDD 三步

```
红：写一个会失败的测试（先证明它真能失败）
绿：用最小改动让它通过
重构：在测试保护下改结构
```

### 5.3 好断言的三个特征

| 特征 | 说明 | 反例 |
|---|---|---|
| 测业务真相 | 断言"数字对得上" | `assert r.status_code == 200` |
| 可失败 | 改坏实现它必须红 | 断言恒真 |
| 快速定位 | 失败信息能指向原因 | `assert result` |

### 5.4 缺陷分级

| 级 | 定义 | 响应 |
|---|---|---|
| S1 安全 | 红线可绕过/停机失效 | 停止发布，立即修 |
| S2 功能 | 主链路断裂 | 当迭代修 |
| S3 一般 | 非主链路 | 排期 |
| S4 体验 | 文案/提示 | 累积 |

## 6. 学生任务（Arbeitsauftrag）

**必做**：给一个现有功能补 1 个单测，必须提交"红→绿"两次运行截图。
**必做**：跑一次 E2E，把其中一条断言改成"业务真相"断言（如看板数字 == API 数字）。
**选做**：给"看板与 API 不一致"设计 3 条 E2E 断言。

---

## 7. 费曼检验

| # | 问题 | 合格标准 |
|---|---|---|
| 1 | 为什么先写测试？ | 能说"先证明测试能失败，才知道它在测什么" |
| 2 | 200 就代表功能对吗？ | 能举"状态码对但数据错"的例子 |
| 3 | E2E 和单测分别抓什么 bug？ | 能说出"集成/界面"vs"逻辑" |

## 8. 评价

| 维度 | 权重 | 观测点 |

| 单测（红→绿） | 35% | 有失败证据、断言有意义 |
